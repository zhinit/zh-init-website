# Portfolio Projects

The projects are the portfolio. Every source agrees on this: 3-5 polished
projects with working demos and clean GitHub repos outperform 10+ basic ones
(source: hakia-developer-portfolio-guide-2026.md). 84% of employers want
working applications, not just code repositories (source:
hakia-developer-portfolio-guide-2026.md, citing Stack Overflow Developer
Survey 2024).

## How many

3-5 projects. Sources converge on this range (source:
hakia-developer-portfolio-guide-2026.md, nucamp-portfolio-projects-recruiters.md,
arc-dev-software-engineer-portfolio.md). Below 3 looks thin. Above 5 dilutes
attention and increases maintenance burden (broken demo links are a major
red flag — source: hakia-developer-portfolio-guide-2026.md).

## What makes a good portfolio project

### It solves a real problem

Over 60% of recruiters specifically seek evidence of real-world problem-solving
(source: nucamp-portfolio-projects-recruiters.md). Tutorial follow-alongs and
todo apps don't count unless 70%+ of the work is original (source:
hakia-developer-portfolio-guide-2026.md). The project should address a genuine
need — even a personal one.

### It has a working demo

A live URL a recruiter can open in a browser. Not a localhost URL. Not a
screenshot. Not "clone the repo and run npm start." 84% of employers want
this (source: hakia-developer-portfolio-guide-2026.md). Deploy everything.

### It has a clean GitHub repo

Well-documented README with: purpose, technologies used, instructions for
running the code, and design rationale (source:
vanderbilt-cs-portfolio-guide.md). Consistent code formatting via linters.
Meaningful commit messages. Automated tests if applicable (source:
kettmann-dont-waste-time-portfolio-website.md).

### It demonstrates depth, not breadth

Show mastery of 2-3 stacks rather than surface familiarity with 10 (source:
hakia-developer-portfolio-guide-2026.md). A frontend-focused student might
show React + TypeScript depth. A backend student might show API design +
database optimization + authentication.

### It has measurable impact

Quantifiable results — performance improvements, user engagement metrics,
error reduction rates — provide concrete evidence (source:
nucamp-portfolio-projects-recruiters.md, figma-portfolio-website-examples.md).
Even for personal projects: "reduced page load time by 60%" or "handles 1000
concurrent connections" is better than "built a chat app."

## Presenting projects

Each project should be a mini case study (source:
nucamp-portfolio-projects-recruiters.md):

1. **What it does** — one sentence
2. **Why you built it** — the problem it solves
3. **Live demo link** — first, prominent
4. **GitHub link** — second
5. **Technologies used** — with brief rationale for each choice
6. **Key technical decisions** — 2-3 interesting challenges and how you solved
   them
7. **What you'd do differently** — shows growth mindset; hiring managers value
   this even for failed projects (source:
   muse-6-hiring-managers-personal-websites.md, Ed Fry quote)

Use language accessible to both technical and non-technical reviewers (source:
nucamp-portfolio-projects-recruiters.md). A recruiter reads the description;
an engineer reads the code.

## Project diversity

~70% of hiring managers want to see different kinds of projects (source:
nucamp-portfolio-projects-recruiters.md). This doesn't mean one React app,
one Vue app, one Angular app. It means different domains or problem types:

- A data-heavy dashboard and a real-time collaborative tool
- A CLI tool and a web application
- An API service and a frontend that consumes it

## Three approaches to sourcing projects

1. **Build from scratch** — a complete project demonstrating your preferred
   stack
2. **Meaningful open source contributions** — improvements to established
   projects in your area (source: arc-dev-software-engineer-portfolio.md)
3. **Showcase public work** — features you contributed to at a job or
   internship, with appropriate confidentiality (source:
   arc-dev-software-engineer-portfolio.md)

For students without work experience, option 1 is primary. A single
well-scoped project with documentation and a working demo is better than
three half-finished ones.

## Anti-patterns

- **Tutorial clones** — copy-paste code from courses without original features
  (source: hakia-developer-portfolio-guide-2026.md)
- **Broken demo links** — signals lack of maintenance; check monthly (source:
  hakia-developer-portfolio-guide-2026.md)
- **Localhost URLs** — not a demo if nobody can visit it
- **No README** — a repo without documentation says "I don't communicate"
- **Skill bar charts** — vague percentages ("85% JavaScript") are meaningless
  (source: arc-dev-software-engineer-portfolio.md)
